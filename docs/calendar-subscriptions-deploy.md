# Выпуск календарных подписок

Подготовлен этап 2: односторонняя подписка на выбранные списки Flow. Изменения делаются в Flow; частоту обновления определяет Apple/Google. Файловый импорт/экспорт продолжает работать независимо.

## Что нужно применить в существующем проекте

1. В [SQL Editor](https://supabase.com/dashboard/project/mkkugfnmohgomwutnkww/sql/new) выполнить **только** содержимое [007_calendar_subscriptions.sql](../supabase/migrations/007_calendar_subscriptions.sql). Старые миграции и setup.sql повторно не запускать.
2. В [Edge Functions](https://supabase.com/dashboard/project/mkkugfnmohgomwutnkww/functions) создать функцию **calendar-feed**. Для деплоя через редактор вставить в index.ts всё содержимое [готового index.ts](../supabase/functions/calendar-feed/index.ts). Этот файл самодостаточный: внешние импорты и установка пакетов на сервере не требуются.
3. Отключить для этой функции **Verify JWT / Verify JWT with legacy secret**. Календарные приложения не отправляют пользовательский JWT; функция сама проверяет секретную ссылку. Для остальных функций настройку не менять.
4. Развернуть функцию. Она использует стандартные серверные переменные SUPABASE_URL и SUPABASE_SERVICE_ROLE_KEY, которые Supabase предоставляет Edge Functions. Ключ не нужно вставлять в код, интерфейс Flow или GitHub.
5. Проверить адрес https://mkkugfnmohgomwutnkww.supabase.co/functions/v1/calendar-feed без token: ожидается 404 с текстом Calendar unavailable. Это подтверждает запуск обработчика, но не заменяет проверку подписки с аккаунтом.
6. После публикации интерфейса открыть «Настройки → Календари → Подписка по ссылке», выбрать списки, пояс и подтвердить доступ. Ссылка показывается только при создании или перевыпуске.
7. Добавить ссылку через «Новая подписка на календарь» в Apple Calendar либо «Другие календари → По URL» в Google Calendar. Проверить появление, перенос, завершение и удаление тестовой задачи после обновления календаря. Выпустить новую ссылку и убедиться, что старая возвращает 404; затем отозвать тестовую подписку.

Полный сценарий с реальными Apple/Google-аккаунтами требует пользовательской проверки: автоматические тесты проверяют формат, HTTP-обработчик, БД и интерфейс с имитацией Supabase, но не периодичность обновления внешних приложений.

## Альтернатива: CLI

Из корня репозитория после авторизации в Supabase CLI:

```sh
npm ci
npm run build:calendar-function
npx supabase login
npx supabase functions deploy calendar-feed --project-ref mkkugfnmohgomwutnkww --no-verify-jwt
```

Миграцию выполнить отдельно первым шагом. Файл supabase/config.toml содержит настройку verify_jwt = false только для calendar-feed.

[Официальная документация деплоя](https://supabase.com/docs/guides/functions/deploy), [переменные окружения](https://supabase.com/docs/guides/functions/secrets), [авторизация функций](https://supabase.com/docs/guides/functions/auth).

## Архитектура и принятые решения

- Случайный токен: 32 криптографически случайных байта. Браузер отправляет в RPC только SHA-256; в БД хранится хеш, исходная ссылка не сохраняется в localStorage/sessionStorage и показывается только в текущем окне.
- Таблица подписок личная, с RLS. Создание проверяет доступ к каждому списку; лимит 10 активных подписок и 50 списков в каждой. Изменение настроек — создание новой подписки и отзыв старой.
- Закрытый RPC resolve_calendar_subscription доступен только service_role. Он получает хеш от Edge Function и заново проверяет владельца/участников списков. Потеря доступа хотя бы к одному выбранному списку закрывает всю выдачу. Возврат доступа восстанавливает её, если подписка не отозвана.
- Отзыв и перевыпуск проверяются до обработки If-None-Match. Ответы имеют Cache-Control: private, no-store. Существующие копии в сторонних приложениях удалить дистанционно нельзя.
- Серверная проекция повторений строит следующие 84 дня по тем же правилам, что приложение. Она не записывает виртуальные задачи в БД и не меняет статистику. Когда Flow позже материализует задачи, UID сохраняются благодаря series_id + series_date.
- Предыдущие 28 дней включают уже сохранённые задачи; отсутствующие прошлые экземпляры сервер не создаёт. Более старые события уходят из подписки, история Flow сохраняется.
- Исключения, удалённые даты, остановленные серии и переносы учитываются. Занятые исходные даты из других списков предотвращают повторное появление перенесённого события; содержимое недоступных списков в календарь не попадает.
- UID стабилен; изменение задачи обновляет монотонный SEQUENCE и DTSTAMP. Удалённая задача отсутствует в следующем полном снимке. HTTP ETag меняется вместе с содержимым.
- Лимиты: 10 000 доступных сохранённых задач, 20 000 с проекцией, 100 000 шагов расчёта. При превышении или невозможном времени на DST выдаётся 503 вместо неполного календаря, чтобы клиент не принял частичную выдачу за удаление событий. Задачи без даты штатно не выдаются.
- Исходник обработчика: supabase/functions/calendar-feed/handler.ts; запуск Deno: entry.ts; готовый index.ts генерируется npm run build:calendar-function. CI проверяет соответствие сборки исходникам.
- Обработчик не журналирует URL, токены и тела событий. Полный URL может попадать в инфраструктурные журналы самого провайдера и историю календарного клиента: доступ к таким журналам должен оставаться административным. Не помещать действующие ссылки в публичные issue, скриншоты и документацию.

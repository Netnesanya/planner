# Развитие базового планнера

Приоритет согласован 15 ноября 2026: без новых внешних сервисов.

## Этап 1 — отмена действий и повторения

Реализовано:
- «Вернуть» для последнего сохранения задачи, смены статуса, переноса, удаления или пропуска. История хранится только до перезагрузки страницы и сбрасывается при смене аккаунта. Следующее действие заменяет предыдущее; это не многошаговый журнал.
- Отмена меняет только затронутые записи. При конфликте она отклоняется целиком; остальные изменения сохраняются.
- Локальная отмена повторно читает хранилище. Облачная — проверяет снимки и применяет восстановление атомарно с действующими RLS-правами.
- В редакторе существующей серии: «Только эта задача» по умолчанию и «Эта и будущие». Правило повторения меняется во втором режиме. Для прошлых экземпляров доступен только первый.
- Изменение будущей серии сохраняет выполненные, начатые и отдельно изменённые экземпляры, а также пропущенные даты.
- «Пропустить это повторение» убирает конкретный день. Пропуск/удаление первого дня переносит шаблон на будущий экземпляр: серия продолжает появляться на горизонте 12 недель.
- Перенос и inline-изменения применяются только к выбранной задаче. При отдельном изменении первого экземпляра он становится самостоятельной задачей, а шаблон переносится вперёд.

### Выпуск в существующий Supabase

В SQL Editor выполнить только `supabase/migrations/008_task_undo.sql`. Полный `setup.sql` повторно запускать нельзя: он для пустой базы.
Также обновить Edge Function `calendar-feed` из `supabase/functions/calendar-feed/index.ts`: серверное продление месячных повторов теперь учитывает исходный день месяца после пропуска первого экземпляра. Инструкция деплоя — `docs/calendar-subscriptions-deploy.md`.
Без миграции обычные действия и управление повторениями работают; облачная кнопка «Вернуть» выдаёт сообщение о необходимой миграции, не меняя данные.
Восстановление удалённой задачи другого автора в общем списке может быть отклонено существующей политикой создания задач. Отмена не обходит права доступа.
Проверено локально и на PostgreSQL через PGlite; реальный облачный аккаунт требует проверки после применения миграции.

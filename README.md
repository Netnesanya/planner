# Flow Planner

Планнер на Angular с тёмной темой. Работает локально без регистрации; Supabase подключается отдельно. Статическая сборка подходит для GitHub Pages, в том числе для адресов вида `username.github.io/planner/`.

Планы развития: [интеграция с Apple и Google Calendar](docs/calendar-integrations-plan.md) — варианты импорта/экспорта, этапы синхронизации, оценки и ограничения.

## Возможности

- Списки, теги, поиск, приоритет 0–5 звёзд, заметки и подзадачи.
- Список, канбан, календарь (день / неделя / месяц), таймлайн целей на 12 недель: один список — одна строка.
- Перенос между колонками, датами и списками; ручная сортировка задач перетаскиванием.
- Изменение длительности за заметный нижний край события вертикального календаря. Шаг — 15 минут; ручки также работают с клавиатуры.
- Выпадающие пресеты длительности (5/15/30/45 минут, 1/1,5/2/3 часа и далее) и ручной ввод в карточке и редакторе: `90`, `1:30`, `1ч 30м`, `1.5h`.
- Прозрачность фона зависит от звёзд: 2.5%, 12%, 30%, 50%, 75%, 100%. Сам текст не становится прозрачным.
- Прогресс (completion ratio) конкретной задачи: ручной ползунок или измеримая цель — например, `3 500 / 5 000 $`. Фактическое значение редактируется прямо в карточке. Завершение не меняет достигнутое значение.
- Повторение каждый день, по будням, еженедельно и ежемесячно.
- История, completion rate за период, график выполнения, активность за 12 недель, серия дней с выполнением.
- Фокус-таймер, экспорт / импорт JSON, адаптивный интерфейс.
- Личные и общие списки с отдельными аккаунтами Supabase Auth и серверными RLS-политиками.

## Запуск

Нужен Node.js 24 (версия указана в `.nvmrc`).

```sh
npm ci
npm start
```

Открыть `http://127.0.0.1:4200`. При первом запуске появятся примеры. **Настройки → Пространство → Очистить локальные данные** создаёт пустое пространство. Перед очисткой можно экспортировать JSON.

Для подключения Supabase локально скопируйте `.env.example` в `.env.local` и заполните URL и publishable key. `npm start` и `npm run build` создают `public/config.js` автоматически. Оба файла исключены из Git. Публичный ключ всё равно виден в браузере; доступ к данным ограничивают Auth и RLS. Серверные ключи сборка отклоняет.

```sh
npm run build          # production: dist/planner/browser
npm run preview        # проверить production на http://127.0.0.1:4173/planner/
npm test               # доменная логика + PostgreSQL/RLS через PGlite
npx playwright install chromium
npm run test:e2e       # браузерные сценарии, приложение должно работать на :4200
```

Для другого адреса тестов: `FLOW_TEST_URL=http://127.0.0.1:4173/planner/ npm run test:e2e`.

## Supabase

1. Создайте Supabase-проект.
2. Для нового пустого проекта выполните **`supabase/setup.sql`** в **SQL Editor** один раз: файл устанавливает все три миграции одной транзакцией. Он генерируется командой `npm run db:bundle`. Для существующей установки выполняйте только ещё не применённые файлы из `supabase/migrations/` по порядку: `001_planner.sql`, `002_goals_and_cycles.sql`, `003_recurrence_horizon.sql`. Схема включает таблицы, функции, RLS, триггер для новых аккаунтов и Realtime.
3. В **Authentication → URL Configuration** укажите URL приложения в Site URL и разрешённых Redirect URLs. Для разработки добавьте `http://127.0.0.1:4200/`, для Pages — полный URL с именем репозитория и завершающим `/`.
4. В приложении откройте **Настройки → Аккаунт и синхронизация**. Укажите Project URL и публичный **publishable / anon key**. Не используйте `service_role` или `sb_secret_…`.
5. Зарегистрируйте два аккаунта; при включённом email confirmation подтвердите адреса. Вход — email + пароль.
6. Владелец создаёт список и открывает **Настройки списка → Общий доступ**, затем вводит email уже зарегистрированного второго аккаунта. Оба участника смогут читать, создавать, менять и завершать задачи этого списка. Управлять доступом и названием списка может владелец.
7. Второй аккаунт нажимает кнопку облака или возвращается в окно приложения, чтобы обновить доступные списки. Изменения задач синхронизируются через Realtime; есть ручное обновление и обновление при возврате в окно.

Схема:

| Таблица | Данные и доступ |
| --- | --- |
| `lists` | Списки. Владелец или явный участник читает; владелец управляет списком. |
| `list_members` | Участники. Добавление и удаление только проверенными RPC владельца. |
| `tasks` | Задачи, повторения, длительность, прогресс, теги, подзадачи, история. Доступ через список. |
| `preferences` | Настройки конкретного пользователя. |
| `planning_cycles` | Личные 12-недельные циклы, связанные цели и письменные итоги недель; RLS по владельцу. |

Локальные примеры не загружаются в облако автоматически. После выхода возвращается отдельное локальное пространство. Облачные данные не записываются в localStorage; сессию Auth хранит SDK. Для облачных изменений нужен интернет, очередь офлайн-изменений не реализована. Локальный режим сохраняет данные в браузере и поддерживает резервные копии.

RLS и функции проверяются тестами на настоящем PostgreSQL-движке PGlite с ролями `anon` и `authenticated`, тремя пользователями и запретом доступа к чужим данным. Подключение к конкретному Supabase-проекту необходимо отдельно проверить после создания проекта.

Официальные материалы: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Supabase Auth](https://supabase.com/docs/reference/javascript/auth-signinwithpassword).

## GitHub Pages

1. Загрузите файлы проекта в репозиторий, основная ветка — `main`.
2. В **Settings → Pages → Build and deployment → Source** выберите **GitHub Actions**.
3. При желании добавьте **Settings → Secrets and variables → Actions → Variables**:
   - `SUPABASE_URL`
   - `SUPABASE_PUBLISHABLE_KEY` — публичный ключ `sb_publishable_…` (старое имя `SUPABASE_ANON_KEY` также поддерживается).
4. Push в `main` или ручной запуск workflow **Deploy Flow to GitHub Pages** запускает проверки, сборку и публикацию `dist/planner/browser`.

Без переменных сайт работает локально, а Supabase можно подключить в настройках. `scripts/write-config.mjs` формирует публичный `config.js` и отклоняет серверные секретные ключи. GitHub Pages — только хостинг интерфейса; авторизацию и доступ к данным проверяет Supabase.

На GitHub Free репозиторий для Pages должен быть публичным. В репозитории находятся код и схема базы, а задачи, аккаунты и пароли хранятся в Supabase. Публичный ключ предназначен для браузера и не заменяет вход пользователя; `service_role`, `sb_secret_…` и пароль базы в проект добавлять нельзя. [О ключах Supabase](https://supabase.com/docs/guides/getting-started/api-keys).

`baseHref: "./"` и отсутствие URL-маршрутов позволяют размещать приложение в подпапке без серверных rewrite-правил. Обновление страницы и ссылки подтверждения Auth не требуют SPA fallback.

## Повторения и метрики

- Повторения заранее создаются на 84 дня от текущей даты. При открытии приложения горизонт продлевается. Каждое повторение — отдельная задача с собственным выполнением и прогрессом; задачи без времени видны в строке «Без времени».
- Для месяца сохраняется исходный день: 31 января → 28/29 февраля → 31 марта.
- Завершение и его отмена меняют только конкретный экземпляр и не создают дубликатов. Изменение правила повторения перестраивает будущие неизменённые задачи серии; выполненные и индивидуально изменённые сохраняются. Удаление экземпляра запоминается, чтобы он не возник снова при продлении горизонта. Удаление исходного экземпляра прекращает продление серии, оставляя уже созданные повторы.
- Completion rate за период = выполненные в периоде / (выполненные в периоде + незавершённые задачи со сроком в периоде). Даты завершения учитываются в локальном часовом поясе.
- Completion ratio задачи = фактическое значение / цель. Визуальная полоска ограничена 100%, но фактическое значение может превышать цель. У ручного ползунка диапазон 0–100. Закрытие задачи сохраняет частичный результат.
- «Объём выполненного» — плановая длительность завершённых задач; это не фактический тайм-трекинг.
- Таймлайн показывает только майлстоуны по неделям, с точной датой на маркере. Обычные действия остаются в списках/канбане/календаре. Таймер работает, пока приложение открыто, и не пишет фактическое время в задачи.
- В вертикальном календаре перенос и растягивание используют Pointer Events: сохраняется точка захвата, положение верхнего края переводится в минуты, шаг 15 минут, видны точное время и предпросмотр. Работают мышь/касание, автопрокрутка и Escape для отмены. Перенос между списками, колонками канбана и ячейками месяца/таймлайна использует HTML Drag & Drop для мыши.

## Майлстоуны и 12-недельный год

В редакторе две карточки типа: **Задача** (по умолчанию) и **Майлстоун**. Майлстоун — результат к дате, без времени начала и длительности в интерфейсе. Название и цвет образуют тег; назначьте его обычной задаче через поле «Тег майлстоуна» из любого доступного списка. Ввод точного уникального имени майлстоуна в обычные теги также связывает задачу. Связь хранится по `goal_id`, поэтому переименование и смена цвета обновляют все связанные карточки. Один экземпляр действия связан с одним майлстоуном. В карточке майлстоуна раскрывается список связанных задач, которые можно отмечать выполненными.

Верхний переключатель **Планнер / 12 недель** открывает отдельный экран:

1. Создайте цикл с названием, датой начала и своим «зачем». Горизонт — ровно 84 календарных дня, в том числе через Новый год и смену часового пояса/DST.
2. Добавьте несколько измеримых целей. Новая цель автоматически входит в текущий цикл; существующие выбираются явно.
3. Спланируйте действия по дням недели и диапазону недель. Серия создаётся заранее (например, 3 тренировки × 12 недель = 36 задач), чтобы пропуски оставались видны. Распределите время в календаре.
4. Показатель недели = выполненные связанные действия с датой в этой неделе / все такие запланированные действия. Без плана отображается «—». Обычная рутина и сами цели не входят в знаменатель. Прогресс результата, например 70 / 90 кг, ведётся отдельно.
5. Сохраняйте письменные итоги недели: что получилось и что изменить. Завершённый цикл остаётся доступным в селекторе, задачи и итоги сохраняются.

Это адаптация принципов методики: видение → цели → недельные действия → измерение выполнения → обзор. 85% показаны как ориентир регулярности, не обещание результата. Вдохновлено [официальным описанием недельной практики](https://academy.12weekyear.com/wp-content/uploads/2021/07/DIY-Participant-Workbook-Final-4.17.20-copy.pdf) и [статьёй авторов о выполнении и результатах](https://12weekyear.com/post/the-game-of-work). Интерфейс и формулировки самостоятельные.

Недельный показатель пересчитывается по текущему плану: перенос, удаление или отвязка задачи меняют знаменатель; это не замороженный исторический снимок. Обычные повторяющиеся задачи тоже видны на 12 недель вперёд. «Запланировать действия» удобнее для сочетания нескольких дней недели и ограниченного диапазона недель конкретного цикла. Циклы и обзоры личные, задачи могут находиться в общих списках. Циклы входят в JSON-экспорт и импорт; старые резервные копии продолжают открываться.

## Организация кода

```text
src/app/
  app.component.*              оболочка, навигация, настройки и общий доступ
  planner.service.ts           операции с локальным хранилищем и Supabase
  models.ts                    типы, даты, повторения, метрики, валидация
  planning.ts                  границы циклов, недельный счёт и серии действий
  recurrence.ts                горизонт повторений, исключения и изменения серии
  focus.service.ts             таймер, сохраняющийся при смене экрана
  task-card.component.*        карточка, звёзды и быстрый ввод длительности
  editor/task-editor.*         редактор задачи
  shared/                      звёзды, прогресс, общий контракт task-view
  views/                       отдельный компонент / HTML / SCSS каждого экрана
src/styles/
  _tokens.scss                 цвета и --font-scale (сейчас 1.14)
  _base.scss                   reset и общие кнопки/поля/диалоги
supabase/migrations/           схема и серверные права доступа
```

Стили экранов инкапсулированы Angular. `ViewEncapsulation.None` и `::ng-deep` не используются. Общие стили содержат только повторно используемые примитивы; размеры сводки редактируются в `today-summary.component.scss`, карточки — в `task-card.component.scss`. Шрифт Manrope поставляется локально в сборке, внешний Google Fonts не нужен.

## Текущие границы

Это самостоятельный планнер в духе TickTick, без интеграции с самим TickTick. Здесь пока нет push-напоминаний при закрытом браузере, импорта внешних календарей, вложений и конфликт-резолюции одновременного редактирования одного поля. Серверные RLS-политики остаются обязательными даже при использовании двух знакомых пользователей.

## Личные финансы

Раздел «Финансы» открывается переключателем рядом с планнером и 12 неделями.
Сначала добавьте счёт, его валюту и начальный остаток. Для нуля оставьте остаток пустым или введите 0.
Далее расход записывается суммой и необязательной категорией; новые категории создаются прямо в форме.
Комментарий, произвольные теги и ежемесячное повторение находятся в раскрываемых подробностях.
Ввод сохраняется как черновик текущей вкладки. Редактирование и повтор доступны из ленты операций.
Переводы поддерживаются между своими счетами в одной валюте и исключаются из доходов/расходов.
Для новых счетов доступны USD, EUR и RSD; по умолчанию выбран USD. Обмена валют и банковской синхронизации пока нет.

Регулярный платёж — отдельный шаблон и устойчивые экземпляры по исходной дате.
Расписание формируется на год вперёд и продлевается при открытии. В коротком месяце число 31
становится последним днём, затем возвращается на 31. Можно оставить сумму неизвестной или задать оценку.
«Оплачено» открывает подтверждение фактической суммы и даты. Расход создаётся только при записи.
Уже записанный расход можно связать с платежом без дублирования. Перенос относится к одному экземпляру;
пропуск сохраняется, отмена операции возвращает платёж в ожидающие. Изменения расписания сохраняют
оплаты, пропуски, просроченные экземпляры и индивидуальные переносы. Приостановка/дата окончания
останавливают будущую генерацию, но не отменяют подписку у поставщика. Напоминания пока только внутри
приложения; push-уведомлений нет. Прогноз на 30 дней учитывает ожидающие платежи, включая неподтверждённые
прошлые; суммы неизвестных платежей показываются отдельно, будущие доходы/обычные покупки не предполагаются.

Локальная книга хранится в IndexedDB (`flow-finance`, `books/local`); чтение и запись выполняются в одной транзакции базы. Предыдущая локальная книга `flow.finance.local.v1` автоматически подхватывается при первом сохранении в IndexedDB. Финансовая копия экспортируется/восстанавливается отдельно
через настройки финансов и **не входит в резервную копию задач**. Перед заменой книги скачайте её копию.
Облачная книга привязана к пользователю, не разделяется с участниками списков и не смешивается с локальной.
Для существующей Supabase-базы примените `supabase/migrations/004_finance.sql`; для новой используйте
обновлённый `supabase/setup.sql`. Обновления используют revision/CAS; при конфликте данные не перезаписываются,
форма остаётся открытой. Удалённая миграция автоматически не применяется. Проверки PostgreSQL выполняются
в PGlite; реальный Supabase требует отдельного smoke test после установки миграции.

Проверки: `npm test`, `npm run test:e2e`, `npm run test:finance`, `npm run test:mobile`.
Финансовый браузерный тест покрывает WebKit 320/390/430 px и Chromium desktop, включая две вкладки.
Это эмуляция WebKit, а не доказательство поведения клавиатуры/панелей Safari на физическом iPhone.


### Финансовые теги

Теги доходов и расходов выбираются из отдельных всплывающих списков в форме операции.
Новый тег можно создать там же или заранее в «Финансы → Настройки → Теги финансов».
Одинаковое название в расходах и доходах означает два независимых тега.
Список упорядочен по числу сохранённых операций своего типа с тегом; при равенстве — по алфавиту.
Редактирование и удаление операций пересчитывают частоту; выбор в форме и несохранённый черновик её не увеличивают.
Теги старых операций доступны без изменения истории. Регистр и повторные названия не создают двойной счёт.
У расходных тегов есть оценка 0–5: 0 — вредное, 1 — лишнее, 2 — иногда можно,
3 — допустимо, 4 — важно, 5 — необходимо. Шкала состоит из пяти звёзд.
Левые 30% видимой звезды выбирают предыдущее значение (левая часть первой — 0),
остальные 70% — значение самой звезды. При наведении подсветка и текст показывают
предварительную оценку, при уходе курсора — сохранённую. Контур указывает звезду под курсором,
даже если заполненных звёзд ноль. Полный повторный клик не сбрасывает оценку.
Для клавиатуры: стрелки меняют значение, Home выбирает 0, End — 5.
Оценка относится к тегу и не влияет на частотную сортировку. У доходных тегов шкалы расходов нет.
Реестр и оценки включены в финансовую копию и в приватную облачную книгу; новая SQL-миграция не нужна.
Проверка UI тегов: `npm run test:finance:tags` (WebKit 320/390/430 px, Chromium desktop).


### Плавное раскрытие и селекторы

«Комментарий и повторение» анимирует реальную высоту блока за 240 мс, поэтому высота
модалки плавно следует за содержимым и ограничивается viewport. При reduced motion
раскрытие мгновенное. Повторное нажатие во время анимации меняет направление;
закрытие диалога отменяет незавершённую анимацию.
Стрелка нативных селекторов имеет общую геометрию в `src/styles/_base.scss`;
контекстные стили не должны сбрасывать её через background shorthand или сжимать правый отступ.
Проверка: `npm run test:ui` — промежуточные высоты при открытии/закрытии, быстрый повтор,
reduced motion, отступ подписи суммы и выбор в Фокусе/редакторе на мобильном WebKit и Chromium.


### Накопления

«Финансы → Накопления» содержит денежные цели с целевой суммой и резервами на счетах
той же валюты. Резервирование не меняет остатки и не создаёт расход/доход; свободная сумма
равна остатку минус резервы всех накоплений. Нельзя зарезервировать чужой резерв или
освободить больше своей суммы. Конвертация валют не предполагается.
Фактическую покупку разрешено записать даже при возникновении дефицита резервов:
отрицательная свободная сумма видна в накоплениях и обзоре; новые резервы блокируются.
В архив можно убрать только накопление с нулевым резервом. Сумма цели может быть превышена.
Накопления входят в финансовый JSON, облачную книгу и финансовую резервную копию;
старые книги без поля `savings` остаются совместимыми. Дополнительная финансовая SQL-миграция не нужна.
